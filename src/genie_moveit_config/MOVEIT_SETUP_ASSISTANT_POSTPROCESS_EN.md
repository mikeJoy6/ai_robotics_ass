## §1 `config/<robot>.ros2_control.xacro`

As generated:

```xml
<xacro:property name="initial_positions" value="${load_yaml(initial_positions_file)['initial_positions']}"/>
<ros2_control name="${name}" type="system">
    <hardware>
        <!-- By default, set up controllers for simulation. This won't work on real hardware -->
        <plugin>mock_components/GenericSystem</plugin>
    </hardware>
```

### §1a `load_yaml` → `xacro.load_yaml`

```xml
<xacro:property name="initial_positions" value="${xacro.load_yaml(initial_positions_file)['initial_positions']}"/>
```

Reason: bare `load_yaml()` is deprecated and prints `warning: Using load_yaml() directly is deprecated` on every expansion.

### §1b Replace `<plugin>` with `<plugin_class>`

- The string must match `<class name="...">` in `<hw_pkg>`'s plugin xml character for character. pluginlib looks up by class name; the package name is irrelevant.
- Known values:

| Robot | `<plugin_class>` | `<plugin_src>` |
|---|---|---|
| G1 (A2D) | `genie_hardware/GenieArmHardware` | `src/genie_robot_agibot_g1_hardware/src/arm_control_ros.cpp` (this repo) |
| G2 | `genie_hardware/GenieG2ArmHardware` | `agi@g2_robot/src/genie_robot_agibot_g2_hardware/src/arm_control_ros.cpp` (not in this repo) |

- A new robot must use a new class name; never reuse `GenieArmHardware`. Reason: sourcing two workspaces at once causes a class-name collision.

### §1c Add every `<param>`

The plugin reads params in `on_init()` with `info_.hardware_parameters.at("<key>")`; any missing key is FATAL (log: `URDF ros2_control 标签中缺少必要参数!`, i.e. "required parameter missing from the URDF ros2_control tag").
Required params = the output of this command, all of them:

```bash
grep -o 'hardware_parameters.at("[^"]*")\|read_bool_param("[^"]*"' <plugin_src> | sort -u
```

Known sets:

- G1: `left_state_topic` `right_state_topic` `neck_state_topic` `body_state_topic` `left_ee_state_topic` `right_ee_state_topic` `command_topic` `head_command_topic` `body_command_topic` `left_ee_command_topic` `right_ee_command_topic` `control_head`
- G2: `state_topic=/gdk/joint_state` `status_topic=/gdk/motion_control_status` `command_topic=/gdk/joint_control` `control_head` `control_body`

Switch params (`control_head`, `control_body`) take the value `$(arg <name>)`; declare them in §2.

### §1d Keep a mock branch (required for new robots; the G1 reference skipped it and hard-codes the real plugin)

```xml
<hardware>
    <xacro:if value="$(arg use_real_hardware)">
        <plugin><plugin_class></plugin>
        <param name="state_topic">/gdk/joint_state</param>
        <!-- remaining params from §1c -->
        <param name="control_head">$(arg control_head)</param>
    </xacro:if>
    <xacro:unless value="$(arg use_real_hardware)">
        <plugin>mock_components/GenericSystem</plugin>
    </xacro:unless>
</hardware>
```

Purpose: `demo.launch.py` still runs as pure simulation.

### §1e `<joint>` blocks

Do not change their content (command_interface position; state_interface position, velocity; initial_value).
Do verify three sets are equal: `<joint name>` set in this file = joints in the hardware feedback = union of joints across SRDF planning groups.
Known omission: G1 gripper joints `left_narrow2_joint`, `right_narrow2_joint` had to be added by hand.

`CHECK` (§7 commands 1 and 2): real mode `<hardware>` contains `<plugin_class>` and every §1c param; default mode is mock; no deprecated warning.

## §3 `config/joint_limits.yaml`

### §3a Every number must be a float literal

The generator writes integers (e.g. `max_acceleration: 0`, `max_velocity: 3`). MoveIt declares these params as double; integers cause:

```
parameter 'robot_description_planning.joint_limits.xxx.max_acceleration' has invalid type: expected [double] got [integer]
```

Effect: move_group fails to start, or that joint's limit is ignored.

Rule: `max_velocity` `max_acceleration` `min_position` `max_position` always carry a decimal point (`0`→`0.0`, `5`→`5.0`).

### §3b Enable acceleration limits

As generated: `has_acceleration_limits: false` + `max_acceleration: 0`. TOTG time parameterization needs an acceleration bound; without it trajectories are too aggressive or you get `No acceleration limit was defined`. Change every joint to:

```yaml
  <joint>:
    has_velocity_limits: true
    max_velocity: <value from table>
    has_acceleration_limits: true
    max_acceleration: <value from table>
```

Values (G1 reference; for a new robot map by joint type; if unsure use the smaller value):

| Joint type | max_velocity | max_acceleration |
|---|---|---|
| Arm (7 joints) | 5.0 | 1.0 |
| Head | 1.0 | 1.0 |
| Waist / lift | 0.10 | 0.10 |
| Gripper | 10.0 | 2.0 |

Keep `default_velocity_scaling_factor` and `default_acceleration_scaling_factor` at `0.1`.

### §3c Position limits (only when the user asks to narrow them)

`has_position_limits: true` + `min_position` / `max_position` (rad) override the URDF `<limit>`. When changing them, change the URDF too; both must agree. G1 precedent: Joint2 narrowed to ±100°.

`CHECK` (must print nothing):

```bash
grep -nE "(max|min)_(velocity|acceleration|position): -?[0-9]+$" config/joint_limits.yaml
```

## §5 `config/ros2_controllers.yaml`

### §5a `update_rate`

```yaml
controller_manager:
  ros__parameters:
    update_rate: 500  # Hz; generated value is 100
```

Constraint: the plugin's `write()` moves at most `STEP_SIZE = 0.01 rad` per cycle (see `<plugin_src>`), so max joint speed = `0.01 × update_rate` rad/s.

| Robot | Feedback rate | update_rate | Max speed |
|---|---|---|---|
| G1 | ≥500 Hz | 500 | 5 rad/s |
| G2 | `/gdk/joint_state` 100 Hz | 100 | 1 rad/s |

Do not set update_rate above the hardware feedback rate unless the user explicitly asks; if they do, tell them to test with small motions on the real robot.

### §5b Add a `joint_state_broadcaster` param block (not generated)

```yaml
joint_state_broadcaster:
  ros__parameters:
    publish_rate: 500    # equals update_rate
```

### §5c Add 3 fields to every JointTrajectoryController

```yaml
left_arm_group_controller:
  ros__parameters:
    joints: [...]
    command_interfaces:
      - position
    state_interfaces:
      - position
      - velocity
    state_publish_rate: 100.0          # new
    action_monitor_rate: 20.0          # new
    allow_partial_joints_goal: false   # new
```

### §5d Gripper controllers (same condition as §4)

1. Declare `left_hand_controller` and `right_hand_controller` under `controller_manager.ros__parameters`, type `joint_trajectory_controller/JointTrajectoryController`.
2. Add their `ros__parameters` blocks (same shape as §5c).
3. Add spawners for them in the hardware launch. G1 precedent: they were configured but not spawned, so MoveIt could not find the action.

`CHECK`: §7 command 4; spawner list in the hardware launch = controller list in `ros2_controllers.yaml`.
